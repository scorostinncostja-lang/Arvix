# 02 · Механики

> Все формулы здесь — из `arvix-claude/arvix/rules.py`, `daily.py`, `load.py`, `core.py`. Если документ и код
> расходятся — прав код, а документ чинится. Числа без пометки «конфиг» зашиты в `rules.py`; то, что меняется
> без правки кода, лежит в `defaults.toml` → `~/.config/arvix/config.toml`.

## 1. Задача — базовая единица

```
Task (state.Task)
  id            8 hex-символов (uuid4[:8])
  title         до 200 символов
  sphere        learning | work | sport | social | health | finance | project | chore
  importance    1..5     4–5 = провал уходит в долг
  difficulty    1..5
  local_date    день задачи
  start         «ЧЧ:ММ» или null  (без времени — без напоминаний)
  duration_min  минуты
  deep_work     bool     считается в глубокую работу дня и недели
  proof         confirm | report | photo   выводится кодом, см. §1.1
  source        user | recurring (из шаблона) | …
  tags          novelty, offscreen — считаются в квоты
  status        planned → active → done | failed | debt | cancelled | written_off
  actual_start, done_pct, report, debt_since, reason, focus_min
```

### 1.1. Уровень подтверждения — `rules.derive_proof` ✅

| Условие (проверяется в этом порядке) | proof | Что спрашивает бот |
|---|---|---|
| `deep_work = true` | `report` | «Одним предложением: что именно сделано?» |
| importance ≥ 4 **или** sphere = sport | `photo` | «Фото с подписью. Или одним предложением — что сделано» |
| importance = 3 | `report` | одно предложение |
| остальное | `confirm` | кнопка ✅ |

Правила закрытия (`Core.complete_task`):
- задача с proof `report` или `photo` **не закрывается голой кнопкой** — нужен текст (или фото с подписью);
- фото принимается как отчёт **без проверки**: это ритуал и трение, не верификация (❌ EXIF/pHash/vision, [09-DECISIONS.md D10](09-DECISIONS.md));
- для `photo`-задачи текст вместо фото допустим — тогда `proof_kind = report`;
- `done_pct` 1–100: частичное выполнение считается долей в выполнении дня;
- фокус-таймер по задаче хотя бы на половину её длительности пишется в `task_completed.focus_min` — доказательство
  в журнале, а не множитель очков; отчёт для `report`/`photo` всё равно обязателен;
- закрыть можно `planned`, `active` и `debt`; `done` назад не ходит (инвариант 3).

### 1.2. Статусы и переходы

| Переход | Кто | Событие |
|---|---|---|
| planned → active | кнопка «Начать», `task start`, action `start_task` | `task_started(at)` |
| planned/active/debt → done | кнопка ✅, `/done`, action `complete_task` | `task_completed(done_pct, report, proof_kind, deep_min[, focus_min, doubts])` |
| planned/active → failed или debt | кнопка ❌, action `fail_task`, закрытие дня | `task_failed(reason, debt)` |
| planned → planned (другое время/дата) | «Отложить 15», `defer` | `task_deferred(from, to, date, minutes)` |
| planned/active → cancelled | `cancel` — **причина обязательна** | `task_cancelled(reason)` |
| debt → written_off | `write_off` — обоснование ≥ 20 символов | `debt_written_off(justification)` |

Причина провала, присланная после кнопки ❌, пишется отдельным событием `task_reason` — журнал задним числом не правится.

## 2. Игры нет — ни очков, ни уровней, ни сезонов (D41) ✅

До 18.11 здесь были XP (`10 × K_diff × K_imp × K_proof × K_time`), бонусы дня, уровни и сезоны с рангом. Владелец
убрал игру целиком: «геймификацию полностью (HP, EXP, статус и т. п.), которые могут ошибаться». Довод в пользу —
П4: метрика, которую можно накрутить без движения к цели, не цель; XP считала сам факт нажатия кнопки, а ранг ни на
что не влиял. Что осталось — только факты из журнала:

| Было | Стало |
|---|---|
| XP за задачу, бонусы дня, уровень | ✅ / ❌ и «долг закрыт» — без чисел; выполнение дня в % (доля сделанного) |
| Сезон, SP, ранг | — |
| Серия дней (стрик) | — ; в приложении остался календарь квадратами как **история** работы, без серий и рекордов |
| `/status` с уровнем и HP | **📊 Итоги**: режим, сегодня X из Y, неделя часы из бюджета, сон в среднем против нормы, долг, автономность |
| `K_proof timer` | `focus_min` в `task_completed` — доказательство в журнале |

Старые события `xp_awarded` в журнале остаются (он только дополняется), но в свёртку состояния не входят.
Тесты: `tests/test_no_game.py`, `tests/test_rules.py::NoGameTest`.

## 3. Здоровья (HP) нет — D41 ✅

HP было вторым игровым числом: урон за провалы, игнор, сон, пропущенный разбор, регенерация, щиты, Протокол Ноль
при HP = 0 и 🟥 при HP ≤ 20. Число ошибалось: штраф за неотмеченную задачу, которую сделал, но не нажал; 🟥 по HP,
когда человек выспался (D38). Его функции распределены по тому, что меряет реальность:

| Что делало HP | Кто делает теперь |
|---|---|
| 🟥 при HP ≤ 20 | Burnout Guard по фактам: сон, выполнение, просьба человека (§6) |
| Штрафы и их заморозка | Долг (§4) и его заморозка `rules.frozen`: 🟥, тихий день, ментор выключен, 3+ дня тишины, заявленная причина |
| Щит («заболел» снимает самый крупный урон) | Причина дня (`declare_reason`): важное, не сделанное сегодня, не уходит в долг |
| Протокол Ноль (HP = 0) | — ; его роль — 🟥 и «Вернуться к плану» |
| Урон за сон и поздний отбой | Сон — вход Burnout Guard и автонагрузки (§5, §6, §7) |
| Урон за пропущенный разбор | — ; разбор остаётся вопросом бота, без цены |

Старые события `hp_changed`, `shield_used`, `protocol_zero` в журнале остаются, но в свёртку не входят и режим не
трогают (`test_old_hp_events_do_not_drive_the_mode`).

## 4. Долг ✅

Провал задачи importance ≥ 4 (кнопкой, action'ом или при закрытии дня, когда бот спрашивал) — она **не исчезает**,
а переходит в `debt` с `debt_since`.

- Долг виден в брифинге, контексте модели, `/day`, строке состояния.
- **Пока в долге ≥ 2 задачи**, новые задачи сферы `social` от человека не создаются: `Core.add_task` отказывает
  с объяснением. Задачи из шаблона (`task_source = recurring`) и другие сферы — создаются. Это единственный
  запрет, живущий в коде, и у него есть выход: закрыть долг или списать. **В 🟥 запрет снят:** там живые
  люди — часть восстановления, а не «необязательное».
- Неотчитанная задача уходит в долг при закрытии дня, только если бот в этот день писал и долг не заморожен
  (`rules.frozen`): в 🟥, в тихий день, при выключенном менторе и с третьего дня тишины бот о задачах не напоминает,
  а при заявленной причине дня («заболел») человек честно сказал, почему не смог, — долга нет. То же для кнопки ❌.
- Закрыть долг — выполнить (`complete_task` работает для `debt`, в ответе «долг закрыт»).
- Списать — `write_off` с письменным обоснованием ≥ 20 символов. Обоснование уходит в разбор.

Долг — не очки, а запись «важное не сделано»: он мешает делать то, что хочется, и требует решения, а не наказания.

## 5. Нагрузка: автонагрузка вместо жёстких часов ✅

Человек не задаёт часы. Шаблоны дней — структура (когда и что), а **объём** каждого канала задаёт коэффициент,
который код пересматривает раз в неделю по фактам (`load.py`).

### 5.1. Каналы и старт

| Канал | Что попадает | Старт |
|---|---|---|
| `deep` | блоки с `deep_work` | 0.7 |
| `learning` | sphere `learning` без deep_work | 0.7 |
| `sport` | sphere `sport` | 0.7 |
| `rest` | `health`, `social`, теги `offscreen`/`rest` | 1.0 |
| `other` | остальное | 1.0 |
| `fixed` | школа, дорога, еда, работа, смена, репетитор, секция — флаг `fixed: true` или очевидное название (`FIXED_TITLE`, с границами слов: «Среда: английский» не обязательное) | не масштабируется никогда |

Старт 0.7 — потому что люди переоценивают силы. Диапазон коэффициентов 0.5–1.5, шаг 0.05, блок не короче 15 минут,
длительность округляется до 5 минут.

**Обязательное — занятое время, а не задача.** Блок `fixed` не превращается в задачу: ни напоминаний, ни «Сделано?»,
ни отчёта, ни долга. Модель видит его строкой `ЗАНЯТО: 08:30–14:30 Школа`, инструмент `check_request` — как
конфликт, автонагрузка — как канал `fixed`. Бюджет недели — **только своё время**, без школы и смен. `/schedule`
показывает длительность своих блоков так, как её поставит автонагрузка: «90→65 мин».

### 5.2. Еженедельный пересмотр — `load.review`

Срабатывает при любом `refresh` через 7 дней после прошлого (`budget_set.since`), только если есть шаблоны.
Входы: план/факт по каналам за неделю (без `fixed`), дни с данными, дни 🟥 и 🟨, средний сон против нормы.

| Сигнал | Действие |
|---|---|
| < 4 дней с задачами | держим как есть |
| **перегруз:** 🟥 ≥ 2 дн · 🟨 ≥ 3 дн · недосып > 60 мин | работа (`deep`, `learning`, `other`) × 0.8, отдых × 1.2; при недосыпе > 60 мин спорт × 0.9; серии роста обнуляются |
| **первые признаки:** любой 🟥/🟨, недосып > 30 мин | работа × 0.9, отдых × 1.1 |
| иначе, по каналу (план ≥ 60 мин): выполнено < 50 % | канал × 0.85 — план не по силам |
| выполнено ≥ 85 % **две недели подряд** | канал × 1.1 (не для `rest`) |
| 50–85 % | ничего: один плохой день план не дёргает |

Снижаем быстро, растём медленно. Перемена приходит одной строкой в утреннем брифинге с причиной
(`budget_set.change`, `.reason`).

### 5.3. Предупреждения о перегрузе — `Core.load_check` ✅
В контексте модели строкой ⚠️: неделя запланирована > 110 % бюджета; день > `max(90, бюджет/5 × 1.5)` минут
(в 🟨 × 0.7); глубокой работы > 4 ч в день; задача заканчивается меньше чем за час до целевого отбоя.

### 5.4. Без шаблонов
Бюджет недели — `profile.week_budget_min` (из ответа на вопрос «сколько часов готов учиться», берётся **меньшая**
из названных цифр) или конфиг `week_budget_min` (26 ч); глубокая работа — 35 % от него или `week_deep_budget_min`.

### 5.5. Типы дней
`study · work · deep · recovery · silent` — ярлыки шаблона для брифинга и контекста. Какие дни недели какие — решает
интервью и человек, не спецификация. Тип `silent` или `silent_weekday` в конфиге делает день тихим автоматически.

## 6. Burnout Guard — выключатель жёсткости ✅

Детерминированный расчёт в `rules.guard_mode`, пересчёт при каждом `refresh`, после записи сна, закрытия и провала
задачи. Режим подставляет тон-блок в промпт — модель его не выбирает. Входы: сон за 3 дня, выполнение закрытых дней
за 7 дней (день без задач — `None`, не считается), ручной SOS. HP во входах больше нет (D41). **Нет данных — нет вывода**: без записанного
сна «давление» невозможно, потому что нельзя сказать «ты выспался», не зная этого.

**У 🟥 есть выход, а не только вход (D38).** До 18.11 🟥 кормил сам себя: в 🟥 нет напоминаний → задачи дня не
отмечены → при закрытии они «провалены» → выполнение 0 % → снова 🟥; а 🟥 по HP ≤ 20 держался, потому что HP не рос
без плана (HP с тех пор убран совсем, D41). Теперь (`Core.recompute_mode`, `Core.guard_completion`):
- день, закрытый в 🟥, в выполнение для Guard не входит (`None`) — бот сам сказал «без плана», провала не было;
- сон < 5 ч три дня подряд снимается сразу, как только записан нормальный сегодняшний;
- **«▶️ Вернуться к плану»** — кнопка человека (не действие модели): снимает ручной SOS и до следующей смены дня
  (`rollover`) держит режим не выше 🟨 (`recovery_started`); ментор, выключенный safety-контуром, так не включается;
- первый день после 🟥 — 🟨 «без разгона», даже если данные говорят 🟦.

Как выйти, код пишет в мягкий контекст строкой «ВЫХОД ИЗ 🟥» (`Core.red_exit`), чтобы голова называла правило,
а не обещала «цифры подтянутся сами». Тесты: `tests/test_recovery.py`.

| Режим | Триггер (проверяются сверху вниз, первый сработавший) | Поведение |
|---|---|---|
| 🟥 **КРАСНЫЙ** | `/sos` или «сегодня без сил» (24 ч) · сон < 5 ч три дня подряд · среднее выполнение < 20 % при ≥ 5 закрытых днях из последних 7 (дни в 🟥 не считаются) | ментор выключен на уровне промпта, долг заморожен, контекст без метрик, напоминаний о задачах и чек-ина нет, отбой — мягкой строкой, одна маленькая вещь на день, тон человеческий; брифинг спрашивает сон, панель — с кнопкой «Вернуться к плану» |
| 🟨 **ЖЁЛТЫЙ** | сон < 6 ч два дня подряд · среднее выполнение за 3 дня в [20 %, 40 %] · «Вернуться к плану» до смены дня · первый день после 🟥 | план −30 % (разумный максимум дня × 0.7), глубокая работа только утром — это инструкция тон-блока, тон твёрдый без давления |
| 🟦 **ДАВЛЕНИЕ** | среднее выполнение за 3 дня < 50 % **при известном сне в среднем ≥ 7 ч**, кроме дня возвращения после 🟥 | максимальная жёсткость: это выбор, а не усталость. Без унижения |
| 🟩 **НОРМА** | всё остальное | требовательный, спокойный, конкретный |

Смена режима — событие `mode_changed(from, to, trigger)`; в Claude Code новый тон-блок приходит хуком на следующем
сообщении. Выключенный ментор (§6.1) по тону равен 🟥 независимо от режима (`Core.effective_mode`).

### 6.1. Safety-контур (отдельно от Guard, приоритет выше всего) ✅

| Шаг | Реализация |
|---|---|
| Детекция | `safety.detect` — список маркеров (мысли о смерти, самоповреждение, «нет смысла жить»…) в коде, без модели; плюс сама модель может вызвать `safety_flag` с уровнем `high`/`critical` |
| Действие | событие `safety_flag(level)` → `mentor_enabled = false`; бот отвечает шаблоном `tpl.safety`: это не то, с чем справляется бот, рядом должен быть живой человек (контакт из ответа на вопрос `support`), при угрозе жизни — 112. Голова в этот момент **не вызывается** |
| После | тон 🟥 везде, долг заморожен, напоминания и чек-ин не идут, разбор — один вопрос «как ты» без цифр |
| Возврат | **только человеком**: `/mentor on` или `arvix mentor on`. Инструмента для модели нет; `profile_set("mentor_enabled")` отклоняется |
| Уровни `info`/`low` | не беда, а сведения («кому написать, если станет плохо») — пишутся фактом памяти, ментор не выключается |
| Анализ | `ANALYST_RULES`: периоды с `safety_flag` не разбираются на эффективность |

Ложное срабатывание стоит дёшево, пропуск — дорого. Без этого контура систему с претензией на ментора писать нельзя.

## 7. Сон и отбой ✅

### 7.1. Норма сна — `Core.sleep_target`
1. `profile.sleep_target_min`, если задано явно;
2. иначе расстояние между целевыми отбоем и подъёмом из интервью (вопрос `sleep`: «хочу 23:00–07:30» → 510 мин),
   если оно в пределах 4–12 ч;
3. иначе конфиг `sleep_target_min` (450 = 7.5 ч).

Норма подростка и взрослого различается — её задаёт распорядок человека, а не константа. На норму завязаны 📊 Итоги
(сон в среднем против нормы) и пересмотр нагрузки.

### 7.2. Ввод
`/sleep 7:30 [00:10]`, ответ на утренний брифинг (бот ждёт `sleep`), свободный текст «спал 6 часов, лёг в час»,
`arvix sleep`, MCP `log kind=sleep`. Форматы длительности: `7:30`, `7.5`, `7ч30м`, `450м`, `6` (число ≤ 24 — часы).
Отбой и подъём словами — `core.parse_sleep_text`, без модели (D38): «лёг в час, встал в 8:30», «с 0:30 до 8:30»,
«0:30–8:30» → длительность через полночь считает код; «8:30 утра», «встал в 9» — это **подъём**, а не 8,5 часа сна:
бот спросит «Во сколько уснул?» и примет ответ «в час»; «23:40» — отбой, бот спросит подъём. Отбой 6–11 без «утра» —
вечер (11 → 23:00), 12 — полночь. Голое число берётся сном только коротким ответом («5 задач сегодня?» — не сон).
Голова пишет сон action `log_sleep` с `duration` или с `bedtime` + `wake`. Диапазон 1 мин — 20 ч. Запись возможна
за другую дату (`date`). Под записью — смена режима, если она случилась: «Сон 8ч00м (00:30–08:30). Режим: 🟥 → 🟨».

**Сон без ручного ввода (D48).** Код собирает ночь сам и спрашивает одним касанием:
- *отбой* — «спокойной ночи», «иду спать», «ложусь» (короткая фраза целиком, `core.is_goodnight`) с 18:00 до
  `sleep_night_end` (05:00) или кнопка «🌙 Ложусь» под напоминанием об отбое → событие `bedtime_noted {at, night}`.
  Отвечает на прощание по-прежнему голова; если бот ждал ответа (разбор, отчёт), прощание ответом не считается (D53); 23:50 — ночь на завтра, 00:40 — на сегодня. Нет «ложусь» — отбоем
  считается последнее действие человека в эту ночь;
- *подъём* — первое действие человека утром (от `sleep_night_end` до `sleep_ask_until`, 14:00);
- *вопрос* — планировщик, раз в день, когда сон не записан и человек этим утром уже что-то сделал:
  «🛌 Ночь: отбой ≈23:50 (…), подъём ≈07:50 (первое сообщение) → 8ч00м. Так?» [✅ Да, 8ч00м] [✏️ Иначе].
  Без догадки (нет одной половины, длительность < 1 ч или > 16 ч) — обычный вопрос. Ответ текстом разбирает
  `parse_sleep_text`, как раньше. В приложении карточка сна нажимается: та же догадка и поля «лёг / встал».

Молча догадка не пишется: последнее сообщение — не момент засыпания, первое — не момент подъёма, а от сна зависит
режим. Записывает только подтверждение — `sleep_recorded`, как при ручном вводе. Из брифинга строка «Сон не
записан» убрана: вопрос приходит отдельно, когда человек уже проснулся (в 🟥 брифинг по-прежнему спрашивает сон).

### 7.3. Реакция (детерминированная)

| Сигнал | Реакция |
|---|---|
| сон < 6 ч два дня подряд | 🟨 |
| сон < 5 ч три дня подряд | 🟥; нормальный сон сегодня снимает его сразу (D38) |
| сон в среднем ≥ 7 ч при выполнении < 50 % | 🟦 «это выбор, а не усталость» |
| недосып в среднем за неделю > 30 / > 60 мин | автонагрузка −10 % / −20 % работы |
| отбой позже цели | видно в разборе и контексте; без штрафа (D41) |

Биометрия с часов, пульс, стресс — ❌ не входят ([09-DECISIONS.md D10](09-DECISIONS.md)). Ручной сон даёт главный вход Burnout Guard.

## 8. Протокол игнора ✅

Молчание = бот писал (`msgs_out > 0`), человек ничего не отправил и не нажал (`user_actions = 0`). Счётчик —
`State.ignore_streak`: серию рвёт только действие человека, а дни, когда бот ничего не отправлял (ноутбук спал,
недельная пауза), её не рвут и не удлиняют.

| День молчания | Что делает бот (`scheduler.tick`) | Долг |
|---|---|---|
| 1 | обычные напоминания; разбор начинается с «Ты сегодня молчишь. Что происходит?» | важное неотмеченное — в долг |
| 2 | только брифинг с префиксом «Второй день тишины…» и разбор; напоминания и чек-ин не идут | в долг |
| 3 | одно сообщение: «Три дня. Я не знаю, что происходит, и это хуже, чем провал. Напиши одно слово» | **заморожен** (`rules.frozen`) |
| 4–8 | одно сообщение в день: «Я здесь.» | заморожен |
| 9+ | «Я здесь.» раз в неделю, пока человек не вернётся | заморожен |
| день возвращения | никаких «Я здесь.»; брифинг, отбой и разбор, но без напоминаний о задачах. В промпт головы добавляется `RETURN_HINT`: никакого разбора прошлого, один вопрос «что случилось», один маленький шаг; разбор пропущенного — не раньше чем через 3 дня стабильной работы | — |

Вернулся на второй день — обычный день: одного дня тишины мало, чтобы менять режим.

Система, которая встречает срыв стеной долгов и упрёков, удаляется. Система, которая встречает одним шагом, переживает срыв.

## 11. Закрытие дня — порядок операций ✅ `daily.close_day`

Запускается `catch_up` из любого процесса для каждого незакрытого дня до вчерашнего (после `rollover`, по умолчанию
04:00; до 04:00 вчерашний день ещё открыт для отчётов), максимум 14 дней назад. Один день — одно `day_closed`.
Пока вчера открыто, его незакрытые задачи живые везде (`Core.open_yesterday`, D53): в приложении — секция «Вчера — не
закрыто», у головы — строка ВЧЕРА НЕ ЗАКРЫТО, в планировщике — «Сделано?» в конце блока, даже если конец уже после
полуночи (задача 23:30–00:10). До D53 такая задача без вопроса уходила в долг. Граница считается в одном месте —
`Core.rollover` / `Core.day_boundary`.

1. Открытые задачи → `task_failed(reason=no_report)`. Долг для важности 4–5 — если бот в этот день писал и долг
   не заморожен (`rules.frozen`: 🟥, тихий день, ментор выключен, 3+ дня тишины, заявленная причина дня).
   Бот не задавал вопросов (выключен, работа только в Claude Code) — долга нет.
2. Воскресенье: квоты (§9) — фактом.
3. `day_closed(date, completion, total, done, deep_min, sleep_min, ignored, frozen, mode)` — только факты (D41).
4. Ежедневная заметка Obsidian за этот день дополняется итогами, если она существует (ошибка записи день не ломает).

Затем `catch_up`: еженедельный пересмотр нагрузки (§5.2); материализация задач сегодняшнего дня из шаблона
(обязательные блоки и блоки, чьё время уже прошло, задачами не становятся; длительности × коэффициенты); пересчёт режима.

В тихий день и при выключенном менторе из проактива остаётся только разбор. В 🟥 — мягкий брифинг без плана,
мягкий отбой и разбор одной фразой «Как ты сегодня?»; напоминаний о задачах, чек-ина и ретро нет.
Месячное ретро 1-го числа — 📋 R8; сейчас — скилл `retro` вручную («итоги месяца»).

### 12.1. Вечерний разбор — сердце системы
Именно он превращает день в данные. Структура (одно сообщение бота, один ответ человека):
1. факты: X из Y, глубокая работа, сон, квоты, долг, импульсивные траты (`tpl.debrief_facts`, код);
2. одна честная оценка дня — не льстивая и не уничижительная (analyst);
3. **два вопроса под этот день**, не шаблонные (analyst; при недоступности головы — два запасных);
4. ответ человека одним сообщением → голова: один вывод «что меняем завтра» и план завтра из блока ЗАВТРА контекста;
5. `debrief_completed(answers, conclusion)` → итог дня и вывод Арвикса в блок `%% arvix:день %%` ежедневной заметки (ответы — только в журнал).

В Claude Code то же делает скилл `debrief` через инструмент `debrief` (`facts` → разговор → `complete`).

## 13. Проверки ввода — Арвикс не верит на слово ✅ `checks.py`

Человек может поставить цель, которая ему не нужна, план, который не выполнить, отчёт, которому не верят цифры.
Молча записать и продолжать — значит дать ошибке съесть неделю. Поэтому несостыковки ищет **код** (детерминированно,
без модели), а **модель** их называет человеку и исправляет ([04-AI-LAYER.md §2](04-AI-LAYER.md#2-конституция-слой-1),
секция `critical_thinking`).

| Что проверяется | Когда сомнение | Где видно |
|---|---|---|
| Цель | нет срока; нет метрики; срок прошёл; срок дальше 3 лет — это мечта; похожа на существующую — дубль; вторая главная; 4-я активная цель года; этап без родителя или позже цели | ответ на запись цели, ПРОВЕРИТЬ в контексте |
| Задача | нет времени начала; время уже прошло; пересекается с другой задачей; попадает на обязательное (школа); кончается меньше чем за час до отбоя; длиннее 3 часов | ответ на запись задачи; внахлёст — и в ПРОВЕРИТЬ |
| Отчёт «сделано полностью» | задача стоит на 18:00, а отмечена в 10:00; с начала прошло меньше половины длительности | ⚠️ под ответом, `doubts` в событии `task_completed` — их видит разбор |
| Сон | меньше 3 или больше 13 часов — похоже на опечатку | ⚠️ под ответом |
| Распорядок | целевой сон меньше 7 часов | ПРОВЕРИТЬ |
| Профиль | ядро знакомства пройдено, а главной цели нет | ПРОВЕРИТЬ |

Правила:
- **Сомнение не блокирует запись.** Отчёт записан, задача создана — но рядом стоит ⚠️, и пропустить его молча модели
  запрещено. Блокировка учила бы врать удобнее; видимое сомнение учит планировать точнее.
- **Исправляет модель, решает человек.** Однозначное (нет срока, блок поверх школы) Арвикс чинит сам и говорит, что
  изменил и как вернуть. Если исправление меняет смысл желания — готовый вариант и одно «да».
- **В 🟥 проверок не видно:** строки ПРОВЕРИТЬ нет в мягком контексте, секции `critical_thinking` — в мягком промпте.
- Сверка цели с главной целью, мечтой и бюджетом часов — суждение, его делает модель по контексту и скиллу `goal`;
  код даёт ей факты.

## 14. Проекты ✅ `arvix/projects.py` (D43, D44, D47)

Проект — то, что человек строит сам: бот, сайт, ролики, подкаст, исследование. **Человек говорит — Арвикс заполняет**
(D47): анкет нет. Проект — это чат с Арвиксом плюс папка в Obsidian. Цифры (время, темп, застой, свободное окно)
считает код.

**Как рождается проект.** Человек пишет одну фразу («хочу снять серию роликов про монтаж, чтобы научиться и найти
людей, до февраля»). Код сразу создаёт черновик (`projects.start`: название из фразы, «зачем» — вся фраза; лимит трёх
активных занят — проект «отложен», а не отказ). Следующим ходом голова в чате проекта получает `<new_project>` и
заполняет всё сама: название, тип любым словом, цели, результат, срок, часы в неделю, цель роадмапа, 3–6 этапов с
критерием, темы «учиться», заметку «План», источники. Человек правит словами. У черновика нет папки, пока Арвикс не
дал проекту имя: папка фиксируется первым настоящим названием и потом не переезжает.

**Папка в Obsidian** — `[vault_paths] projects/<проект>/` (по умолчанию `01_Projects`): главная заметка с блоком
Арвикса `%% arvix:проект %%` (зачем, результат, срок, этапы, учиться, источники — пересобирается кодом после каждой
операции и только если изменилось), «Журнал» (записи и отчёты по блокам), заметки Арвикса (`project_note`: план,
архитектура, конспект, разбор кода) и человека, «Файлы» — всё присланное в чат проекта. Свою нетронутую заметку
Арвикс перезаписывает, правленную человеком — только дописывает; за пределы папки проекта не пишет.

**Чат проекта** — своя нить в общей переписке (`message_in/out.project`): в общем чате её нет, история головы в окне
проекта — только она. В запрос головы кладётся блок `<project>` (`projects.chat_block`): карточка, этапы, учиться,
блоки, журнал, источники, список файлов папки с путями — голова читает их сама и знает, что может менять. Код,
скриншоты, PDF, присланные в чат проекта, ложатся в «Файлы» и читаются головой — так Арвикс «видит код» с телефона.
С ноутбука — Claude Code в папке с кодом и инструмент `project`.

**Статусы для человека — три группы**: «в работе» (`active`), «отложены» (`idea`, `paused`), «завершены» (`done` —
результат есть, `dropped` — без результата; итог обязателен). Внутри журнал прежний.

| Правило | Значение | Почему |
|---|---|---|
| В работе одновременно | ≤ `[projects] max_active` (3) | Распыление — проблема №5. Новый сверх лимита — «отложен» |
| Этап | только с критерием готовности (`dod`) | результат, а не бронь времени (П4) |
| Время проекта | задачи с `project` (сделанная — `duration × pct` или таймер, что больше; несделанная — таймер) + минуты журнала «со слов» отдельно | таймер и блоки надёжнее слов |
| Движение | закрытая задача, таймер, запись журнала, пройденный этап | разговор о проекте, план и правка карточки — не движение: обсуждать можно бесконечно |
| Отчёт по блоку проекта | сразу запись журнала (`project_logged` в той же транзакции) | прогресс виден без второго ввода |
| Застой | ≥ 7 дн без движения | Арвикс пишет сам, раз в неделю на проект: «30 мин сегодня» · «Завтра на час» · «⏸ Отложить» |
| Решение | ≥ 21 дн | прямой вопрос «продолжаем, откладываем или завершаем» |
| Темп | этапов % < времени % − 15 п.п. | «отстаёт» с цифрами; прогноз финиша по скорости этапов |

**Блок в план** (`plan_block`) — первое свободное окно кодом (не раньше 09:00 и текущего времени, мимо задач и
обязательных блоков, конец ≥ 1 ч до отбоя), название — следующий этап.

**Учиться** (`learn_item_set`) — общая очередь тем: из проекта, из цели или вручную. Арвикс добавляет темы сам
(`learn_add`: тема, зачем, источники). «Учить сейчас» ставит учебный блок сферы `learning` с меткой `learn:<id>` в
первое свободное окно — дальше работает существующий урок (06-LEARNING §8: план по минутам, таймер, проверка).
Тема, у которой учебный блок закрыт, считается пройденной без отметки (L0). **Будущая вкладка «Обучение» читает
эту же очередь** — 06-LEARNING §10.

**Источники и примеры** (`resource_set`) заполняет Арвикс по разговору: документация, курсы, инструменты, **чужие
репозитории и работы как примеры** (`kind=example`). Предложенное им помечено «проверь».

**Роадмап проектов** — список вкладки сгруппирован по целям (главная первой, внутри — порядок `order`, ↑↓ в меню
проекта). «✨ предложить» у цели — совет L2 в фоне (`project_roadmap.py`): 3–6 проектов идеями с этапами и
источниками, заметка «Проекты — <цель>» в папке роадмапов.

**Убрано** (D44, D47): деньги, каналы привлечения, импорт и синхронизация своих репозиториев GitHub, формы со
ссылками. Их события в журнале остаются, свёртка их не показывает.

В 🟥 и при выключенном менторе проектов нет ни в контексте, ни во вкладке (правило №5). Код, тексты и дизайн делает
человек (`constitution/partner.md`).
