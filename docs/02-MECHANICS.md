# 02 · Механики

> Все числа ниже — дефолты. Они живут в конфиге (`core/domain/mechanics.yaml`), а не в коде, и меняются без миграций. Формулы — L0, детерминированно.

## 1. Цепочка: от цели к дню

```
Цель (год/квартал, метрика, WOOP)
  └─ Роадмап (этапы, источники, чекпоинты)          — 07-SECOND-BRAIN
      └─ Результат недели (1–3 на цель, с DoD)       — §3, вс планирование
          └─ Задача (DoD, первое действие, слот)      — §4, вечерний разбор
              └─ Старт (кнопка / протокол старта)     — §5
                  └─ Отчёт (сделано / частично / нет) — §4.4
                      └─ Разбор (факты, причины, план на завтра) — §13.4
```

Каждое звено — проверяемое. Задача без связи с результатом недели допустима (быт, учёба по расписанию колледжа), но помечается как «поддержка», а не «движение». Метрики показывают соотношение — если неделя на 90% из «поддержки», цели стоят.

## 2. Цели

### 2.1. Иерархия
`мечта → цель (год) → цель (квартал) → результат недели`. Мечта не обязана иметь метрику; всё ниже — обязано.

### 2.2. Поля цели

| Поле | Обязательно | Пример |
|---|---|---|
| `title` | да | «Фронтенд-джун к июню 2027» |
| `why` | да | «Хочу работу, где расту, а не стою на кассе» |
| `metric` + `target_value` + `current_value` | да (кроме мечты) | «Проекты в портфолио: 0 → 3» |
| `deadline` | да | 2027-06-01 |
| `woop` | да для года/квартала | см. §2.3 |
| `lead_measures` | да для года/квартала | см. §2.4 |
| `status` | да | `active` · `paused` · `done` · `dropped` |

**Лимит активных целей уровня «год»: 3.** Больше — распыление, которое проект и лечит. Четвёртая цель ставится только на паузу одной из трёх.

### 2.3. WOOP — план против препятствий
Метод Габриэлы Эттинген (mental contrasting + implementation intentions) — одна из немногих техник постановки целей с сильной доказательной базой. Заполняется в диалоге при создании цели (L1 задаёт по одному вопросу):

```yaml
woop:
  wish:     "Фронтенд-джун к июню"
  outcome:  "Работа по специальности, деньги на учёбу брата"
  obstacle: "После смены нет сил, и я залипаю в шортсы до часа ночи"
  plan:     "Если вернулся со смены — то телефон на зарядку в коридор и 30 минут на одну задачу из роадмапа, без компьютерных игр"
```

План «если-то» превращается в правило: L0 напоминает его в момент, когда срабатывает «если» (например, задача после смены — напоминание включает текст плана).

### 2.4. Опережающие показатели
Итог (метрика цели) ты контролируешь плохо. Регулярные действия — хорошо. Каждая цель года имеет 1–3 опережающих показателя:

```yaml
lead_measures:
  - { name: "Часы глубокой работы по роадмапу", unit: h,      weekly_target: 8,  source: auto }
  - { name: "Закрытые узлы роадмапа",            unit: count,  weekly_target: 1,  source: auto }
  - { name: "Коммиты в pet-проект",              unit: count,  weekly_target: 10, source: integration }
```

`source`:
- `auto` — считается из событий (фокус-сессии по задачам цели, узлы роадмапа, повторения карточек, языковые сессии)
- `integration` — из внешнего источника через MCP (коммиты GitHub и т. п., 11-INTEGRATIONS)
- `manual` — отметка в TWA одной кнопкой

### 2.5. Ревизия целей
Раз в месяц (§13.6): цель ещё актуальна? WOOP-препятствие ещё то? Показатели двигают метрику? Цель можно поставить на паузу или закрыть как `dropped` — это не провал, а решение. Записывается с причиной.

## 3. Неделя

### 3.1. Недельное планирование (вс, ~15 минут)
Связующее звено между целью и днём. Проходит в чате с подтверждением в TWA.

1. **Цифры недели** (L0): выполнение обязательств, закрытые результаты недели, опережающие показатели против плана, сон, цепочка разборов
2. **Выводы фона** (L2 подготовил заранее): 1–3 наблюдения с доказательствами
3. **Один вопрос:** «Что меняем на следующей неделе?» — ответ сохраняется (`weekly_review_completed`)
4. **Результаты следующей недели:** для каждой активной цели — 1–3 результата с DoD. Бот предлагает кандидатов: следующие узлы роадмапа, незакрытое с прошлой недели, долг. Ты правишь. **Лимит — 5 результатов на неделю суммарно**
5. **Проверка ёмкости** (L0): оценки результатов против свободного времени (шаблоны дней минус занятые слоты календаря). Если план > 80% свободного времени — бот просит урезать: «План 31 ч при 34 ч свободных. Буфера нет — первая же неделя с болезнью сорвёт всё. Убери один результат»
6. **Подтверждение** → `weekly_plan_confirmed`. Результаты становятся кандидатами для вечернего планирования дней
7. **Отчёт свидетелю** (если включён, §10)

Пропущенное воскресенье → в понедельник утром бот предлагает 5-минутную версию: только пункты 4 и 6.

### 3.2. Бюджет времени
Продуктивное время в неделю (своё, помимо колледжа и смен) — **ограничение планирования**, а не цель для героизма.

| Период | Потолок продуктивного времени / нед | Из него глубокая работа |
|---|---|---|
| Месяц 1 | 20 ч | 6 ч |
| Месяц 2 | 24 ч | 8 ч |
| Месяц 3 | 28 ч | 10 ч |
| Месяц 4+ | +2 ч/мес, потолок 40 ч | потолок 16 ч |

- Повышение — **только если 2 последние недели закрыты ≥ 75%** по выполнению обязательств. Иначе потолок держится
- Понижение на одну ступень — после 2 недель подряд < 50%. Это реализм, а не наказание
- В режиме 🟨 недельный потолок × 0.7 до выхода из режима

**Почему не 8/8/8 сразу:** колледж + смены пт–вс. 8 часов своей продуктивной работы поверх этого арифметически невозможны. План, который невозможно выполнить, учит не выполнять планы.

### 3.3. Типы дней
Шаблон дня — это набор **слотов** (время + вид работы) и **занятых блоков** (колледж, смена). Слот — не задача: его заполняют конкретной задачей вечером накануне (§13.4).

| Тип | Когда (дефолт) | Профиль |
|---|---|---|
| **Учебный** | пн–чт | Колледж + 2–3 слота своего, один из них глубокий (90–120 мин) |
| **Рабочий** | дни смен (пт–вс) | Смена + 1 короткий слот (45–60 мин). Реалистичный минимум, не повод для стыда |
| **Свободный** | дни без колледжа и смен | 3–4 слота, один длинный глубокий (3–4 ч) |
| **Восстановительный** | только по Burnout Guard | Сон, движение, люди. Ноль обязательных когнитивных задач |
| **Тихий** | 1/нед, с месяца 2 | Бот молчит, план — подтверждённый накануне (§12) |

Привязка типов к дням недели — в настройках. Занятые блоки подтягиваются из календаря (ICS, 11-INTEGRATIONS §4), если подключён.

## 4. Задача — базовая единица

### 4.1. Поля

```yaml
Task:
  title: str                    # глагол + объект: «Написать Promise.all своими руками»
  outcome: str                  # DoD: что будет существовать, когда сделано
  first_step: str | null        # первое физическое действие на 2 минуты
  sphere: learning | work | project | language | sport | health | social | chore
  goal_id / weekly_outcome_id / roadmap_node_id: uuid | null
  importance: 1..5              # 4–5 = при провале уходит в долг
  estimate_min: int             # оценка
  planned_start: datetime | null
  planned_duration_min: int
  deep_work: bool
  proof: none | confirm | report
  status: см. 03-DATA-MODEL §4
  source: plan | user | l1 | roadmap | debt | partial_tail | inbox | log
  parent_task_id: uuid | null   # для хвостов «частично»
```

### 4.2. Критерий готовности (DoD) — обязателен для задач с `importance ≥ 3` и `deep_work`

| Плохо (бронь времени) | Хорошо (результат) |
|---|---|
| «Учёба 2 часа» | «Конспект главы 3 YDKJS: Async — 5 тезисов своими словами в Obsidian» |
| «Английский» | «30 новых карточек повторено + 15 минут подкаста с выписанными 5 фразами» |
| «Поработать над проектом» | «Форма логина отправляет запрос и показывает ошибку от сервера» |

Если при создании задачи DoD не указан, L1 (или кнопки в TWA) предлагает формулировку. Задачи от L1 без DoD не создаются — инструмент `create_task` требует поле `outcome` для `importance ≥ 3`.

**Правило размера:** задача > 120 минут разбивается. Каждая часть — со своим DoD. «Сделать проект» — это результат недели, а не задача.

### 4.3. Уровень подтверждения (`proof`)

| Условие | proof | Что спрашивает бот |
|---|---|---|
| importance ≤ 2 | `confirm` | Кнопки ✅ / ◐ / ✖ |
| importance ≥ 3 или deep_work | `report` | После ✅: «Одной фразой: что из DoD сделано?» |
| быт, без значения для целей | `none` | Ничего, задача — просто напоминание |

Уровень можно поднять вручную, понизить — нельзя. Фото можно приложить к отчёту как личный артефакт (рисунок, конспект от руки) — без «проверки» (почему — 12-DECISIONS D6).

### 4.4. Три исхода

| Кнопка | Что происходит |
|---|---|
| **✅ Сделано** | `task_completed(result=done)`. Для `report` — FSM ждёт фразу |
| **◐ Частично** | «Что осталось?» → `task_completed(result=partial, left=...)` + задача-хвост (`source=partial_tail`) в кандидаты на завтра |
| **✖ Не сделано** | «Почему?» — кнопки причин (те же коды, что в протоколе старта §5) → `task_failed(reason_code)`. `importance ≥ 4` → долг (§6) |

Никакой самооценки «качества 1–5»: она поощряет завышение и смешивает «сделал частично» с «сделал плохо».

### 4.5. Отмена заранее — это не срыв
Задачу можно отменить или перенести **заранее** (≥ 2 ч до начала) с причиной одной фразой: `task_cancelled(advance_min, reason)`. Это честное перепланирование, оно не считается срывом в метрике обязательств. Но доля отмен видна отдельно, и если она > 30% за неделю, разбор задаёт вопрос: план слишком оптимистичен или ты сливаешься заранее?

### 4.6. Задачи «вне плана»
Сделал что-то полезное без плана — отметь (`/done` текстом или кнопкой в TWA): `source=log`. Это не входит в выполнение обязательств (нельзя накрутить процент постфактум), но видно отдельной строкой и учитывается в опережающих показателях.

## 5. Протокол старта — механика «не могу начать»

Главная точка срыва — начало задачи, а не её середина. Наказание за несделанное не помогает начать; разбор причины и конкретный приём — помогают.

### 5.1. Таймлайн

| Момент | Действие |
|---|---|
| T−5 | `⏱ Через 5 минут: <задача>. Первый шаг: <first_step>` · [▶️ Начать сейчас] [⏳ +15 мин] [↪ Перенести] |
| T+0 | `▶️ Время: <задача> · <длительность>` · [▶️ Начал] |
| T+10, не начато | Протокол: «Не начал. Что мешает?» — 5 кнопок причин |
| T+25, не начато и нет ответа | Задача помечается `not_started` (статус остаётся `planned`, событие `start_missed`). Вопрос переносится в разбор. Больше не дёргает |
| конец блока | `Результат?` [✅] [◐] [✖] (только если задача начата) |

**Задача никогда не переводится в `active` без твоего нажатия** (баг B5). Иначе данные о времени старта врут.

`⏳ +15 мин` доступен не больше 2 раз на задачу — третий перенос предлагает [↪ Перенести на другое время] или [✖ Отменить].

### 5.2. Причины и приёмы

| Причина (код) | Что делает Арвикс | Слой |
|---|---|---|
| **Непонятно, с чего начать** (`unclear`) | «Какое первое действие займёт 2 минуты?» — помогает сформулировать `first_step` | L1 |
| **Слишком большое** (`too_big`) | «Делаем только первые 15 минут. Таймер пошёл.» Предлагает разбить задачу | L0 + L1 |
| **Не хочу / скучно / неприятно** (`aversion`) | Правило 5 минут: «5 минут, потом можешь остановиться — и это будет честно записано как 5 минут». Напоминает твой WOOP-план, если есть | L0 |
| **Нет сил** (`low_energy`) | Короткий чек-ин энергии (1–5). ≤ 2 → предложение поменять на лёгкую задачу из того же дня или сдвинуть; пересчёт Guard | L0 |
| **Другое важнее** (`priority`) | «Что именно?» → перенос с причиной (не срыв) | L0 + L1 |

Коды причин — главные данные для аналитика: «70% срывов стартов по алгоритмам — `unclear`» означает, что задачи по алгоритмам сформулированы плохо, а не что ты ленивый. Директива L2 на следующую неделю: «задачам по алгоритмам — обязательный first_step».

## 6. Долг

Проваленная задача с `importance ≥ 4` не исчезает — уходит в долг (`task_debted`).

- **Решение в течение 48 ч.** Варианты: [📅 Перенести на конкретный слот] [✂️ Разбить] [🗑 Списать с причиной]. Списание требует одной фразы обоснования — она уходит в разбор
- **Без решения через 48 ч** долг становится обязательным пунктом разбора: подтвердить план на завтра нельзя, пока по долгу не выбран вариант. Это трение, а не наказание
- **Время под долг резервируется первым** при планировании недели и дня
- **Перенесён 3 раза** → «Ты переносил это трижды. Задача сформулирована неправильно или не нужна?» — предлагается разбить или списать. Повторный перенос — признак плохой формулировки, а не слабости
- В режиме 🟥 эскалация долга заморожена
- Долг виден в брифинге и в TWA отдельным блоком

Долг давит сильнее любой цифры, потому что он не даёт сделать вид, что задачи не было. Но он не отнимает жизнь: социальные дела и отдых никогда не блокируются.

## 7. Burnout Guard — выключатель жёсткости

Детерминированный расчёт **в L0**, три режима. Режим выбирает тон-блок для L1 и коэффициент нагрузки — модель не выбирает их сама.

### 7.1. Режимы и триггеры

Входы: сон (минуты, из чек-ина), энергия (1–5) и стресс (1–5, опционально) из утреннего чек-ина, выполнение обязательств, ручной SOS, safety-флаг.

| Режим | Триггер (любой) |
|---|---|
| 🟥 **КРАСНЫЙ** | `/sos` · safety-флаг · сон < 5 ч три ночи подряд · энергия = 1 два дня подряд · выполнение < 20% за 7 дней (при ≥ 10 запланированных задачах) |
| 🟨 **ЖЁЛТЫЙ** | сон < 6 ч в 2 из 3 последних ночей · энергия ≤ 2 два дня подряд · стресс ≥ 4 два дня подряд · выполнение 20–40% за 3 дня |
| 🟩 **НОРМА** | всё остальное |

**Нет данных — нет вывода.** Если сон не введён, триггеры по сну не срабатывают; бот один раз спрашивает в брифинге.

**Гистерезис (против дребезга):** выход из 🟥 — только после 2 дней подряд вне триггеров 🟥 или ручным переключением; выход из 🟨 — после 1 такого дня. Вход — сразу.

**Пересчёт:** после утреннего чек-ина, после каждого исхода задачи, в 15:00, в начале разбора. Каждая смена — событие `mode_changed(from, to, trigger)`.

### 7.2. Эффекты режимов

| | 🟩 НОРМА | 🟨 ЖЁЛТЫЙ | 🟥 КРАСНЫЙ |
|---|---|---|---|
| Нагрузка дня | план как есть | −30%: снимаются задачи с низшим приоритетом, глубокая работа только до 13:00 | только сон, еда, движение и **один** маленький результат |
| Новые обязательства от бота | да | нет | нет |
| Эскалация долга | да | да | заморожена |
| Напоминания | все | все | только одно утреннее и одно вечернее |
| Тон L1 | прямой, требовательный | твёрдый, без давления, один вопрос о причине | человеческий, тёплый, без метрик и задач |
| Разбор | полный | короткий | только «как ты?» и сон |

**Реализация — критично:** в 🟥 и при `mentor_enabled = false` тон-блок НОРМЫ физически не попадает в промпт — заменяется блоком восстановления. Это не просьба к модели быть мягче, это другой промпт. Проверяется юнит-тестом на сборщике промпта.

Почему нет отдельного режима «давления» для случая «выспался, но не сделал»: этот случай разбирает протокол старта (§5) — выясняет причину и даёт приём. Давление без диагноза усиливает избегание (12-DECISIONS D3).

### 7.3. Safety-контур (отдельно от Guard, приоритет выше всего)

Если в сообщениях признаки серьёзного состояния — не «устал», а реальная беда (мысли о самоповреждении, суициде, безнадёжность):

1. **Детекция:** список маркеров (L0, регулярки, ru/en) → при срабатывании один вызов роли `cheap` для классификации «есть риск / нет». Пропуск маркера страхуется секцией `<safety_override>` в конституции и инструментом `raise_flag`
2. **Действие (L0, шаблон, не модель):** `safety_flag` + `mentor_toggled(enabled=false)`. Сообщение человеческим тоном: это не то, с чем справляется бот; рядом должен быть живой человек. Контакты из профиля: **номер экстренной службы** (дефолт `112`) и **доверенный человек** (имя + как связаться) — задаются в онбординге, меняются в настройках
3. **После:** все задачи, напоминания, метрики и разборы на паузе. Раз в день одно сообщение «Я здесь. Напиши, когда захочешь»
4. **Возврат** — только вручную в настройках TWA, одной кнопкой с подтверждением. Ложное срабатывание лучше пропущенного
5. **Анализ:** период с safety-флагом исключается из всех метрик и из работы аналитика. Никакого «разбора эффективности» этих дней

Бот не задаёт диагностических вопросов, не оценивает риск словами и не ставит диагнозов. Без этого контура проект писать нельзя — это не опциональная фича.

## 8. Inbox и быстрый захват

Мысль, задача, идея, вопрос «на потом» должны захватываться за 5 секунд — иначе они либо теряются, либо отвлекают от текущего блока.

- **Ввод:** `/in <текст>`, голосовое сообщение с первым словом «запиши», кнопка в TWA. Голос распознаётся через STT (роль `stt`)
- **Во время рабочего блока** любой нерабочий вопрос/мысль бот кладёт в inbox сам: «Записал в inbox. Вернёмся в разборе». Это лечит привычку отвлекаться на каждую возникшую мысль
- **Разбор inbox** — пункт вечернего разбора (если есть элементы): по каждому [→ Задача] [→ Заметка] [→ Вопрос учителю] [🗑]. 2 минуты
- Inbox старше 7 дней без разбора → в недельном планировании
- События: `inbox_captured`, `inbox_processed(action)`

## 9. Честные метрики (вместо XP/HP)

Только показатели, которые нельзя накрутить без полезной работы (фильтр 00-VISION §6). Все считаются проекциями из событий.

| Метрика | Формула | Где видна |
|---|---|---|
| **Выполнение обязательств** | `(done + 0.5·partial) / (запланировано − отменено заранее)` по задачам с `planned_date` = день. Задачи `source=log` не входят | брифинг, разбор, TWA |
| **Результаты недели** | закрыто / запланировано на неделю | разбор, ревью недели |
| **Опережающие показатели** | факт / недельная цель по каждой цели | TWA, ревью недели |
| **Цепочка разборов** | дней подряд с завершённым разбором | брифинг, TWA — главная метрика дисциплины |
| **Стартуемость** | доля задач, начатых не позже T+10 | разбор недели |
| **Движение vs поддержка** | доля времени на задачи, связанные с целями | ревью недели |
| **Сон** | среднее за 7 дней + разброс времени отхода ко сну (σ) | брифинг, TWA |
| **Обучение** | чекпоинты пройдены; карточки: просрочено / повторено; удержание | TWA, ревью недели |
| **Автономность** | выполнение в тихие дни ÷ выполнение в обычные (4 нед.); доля учебных вопросов без `/answer` | месячный разбор |

Чего **нет** и не будет: очков, уровней, рангов, «здоровья», бейджей, рейтингов. Цепочка разборов — единственная «серия», потому что разбор — это минимальное действие, которое держит всю систему.

Цепочка не обнуляется в 🟥 и в дни с safety-флагом — эти дни просто не считаются.

## 10. Внешний свидетель (опционально)

Реальная цена срыва — человек, который видит твою неделю. Это работает сильнее любого счётчика.

- В онбординге или настройках выбираешь свидетеля: друг, брат, наставник
- После недельного планирования бот присылает **тебе** короткий отчёт в формате для пересылки: выполнение обязательств, закрытые и незакрытые результаты недели (с причинами), результаты следующей недели
- Ты пересылаешь его сам (бот не может писать людям, которые его не запускали, и не должен делать это за тебя)
- Если отчёт не переслан до понедельника 12:00 — одно напоминание. Дальше — твоё решение, записывается
- В отчёт не попадают: сон, энергия, заметки, страхи, safety — только задачи и результаты

## 11. Протокол игнора

Ты не отвечаешь боту. Система, которая встречает срыв стеной сообщений, удаляется; система, которая встречает одним шагом, переживает срыв.

Молчание = ни одного сообщения и нажатия с начала дня.

| День молчания | Что делает Арвикс |
|---|---|
| 1 | Обычные напоминания. Вечером вместо разбора: «Сегодня ни одного ответа. Что произошло? Одно слово достаточно» |
| 2 | Только одно утреннее сообщение (план) и одно вечернее. Без эскалации долга |
| 3 | Все напоминания на паузе. Одно сообщение: «Три дня тишины. Не знаю, что происходит, — это важнее любого плана. Напиши одно слово» |
| 4–7 | Одно сообщение в день, без цифр и задач: «Я здесь» |
| 8+ | Одно сообщение в неделю |
| **Возврат** | **Протокол возвращения:** никакого разбора прошлого. Один вопрос «что случилось?» (можно пропустить), один маленький шаг на сегодня, план пересобирается с нуля под текущее состояние. Разбор пропущенного — только после 3 дней стабильной работы и только если хочешь |

## 12. Тихие дни и автономность (с месяца 2)

- **Тихий день:** 1 в неделю (с месяца 4 — до 2). Бот молчит весь день: ни напоминаний, ни брифинга. План — подтверждённый накануне, виден в TWA и на ESP32. Вечером — разбор без оценок: только факты и вывод
- Запуск автоматически по расписанию или вручную (`/silent`). В 🟥 тихий день не назначается
- **Понижение частоты (L0-правило):** если 2 недели подряд стартуемость задач определённой сферы ≥ 90%, напоминание T−5 для этой сферы отключается. Сорвал 2 старта подряд в этой сфере — включается обратно. Уведомление об изменении — в ревью недели
- **Метрика автономности** — §9

## 13. Ежедневный цикл и ритуалы

Все времена считаются от профиля (`wake_target`, `bedtime_target`), а не захардкожены.

| Время (дефолт) | Событие | Слой |
|---|---|---|
| **wake + 10 мин** | Утренний чек-ин (сон, энергия) → расчёт Guard → корректировка плана по режиму | L0 |
| **сразу после чек-ина** | Брифинг | L0 (шаблон) |
| **весь день** | T−5 / T+0 / протокол старта / «Результат?» | L0 |
| **15:00** | Один чек-ин, только если выполнение < 40% и есть ещё задачи | L0 + L1 |
| **bedtime − 75 мин** | Вечерний разбор + план на завтра | L0 (+ L1 для свободных ответов) |
| **bedtime − 30 мин** | «Через 30 минут отбой.» Больше никаких задач | L0 |
| **вс 19:00** | Недельное планирование (§3.1) | L0 + L2 (заранее) |
| **1-е число** | Месячный разбор (§13.6) | L0 + L2 (заранее) |

### 13.1. Утренний чек-ин
Одно сообщение, 10 секунд:
```
Доброе утро. Сон: 23:40 → 07:15 (7ч35м) по плану — верно?
[Да] [Ввести иначе]
Энергия: [1] [2] [3] [4] [5]
```
Без чек-ина Guard считает только по выполнению. Если до первого блока чек-ина нет — один повтор.

### 13.2. Брифинг (шаблон L0, без модели)
```
🟨 Пятница · Рабочий день · ЖЁЛТЫЙ (сон 5ч40м, 2-я ночь) — план урезан на 30%

Вчера: 5 из 7 обязательств. Разбор пройден (цепочка 12).

Сегодня:
1. 09:00 · Алгоритмы: BFS на сетке · DoD: решены 2 задачи с LeetCode, код в репо · ДОЛГ
2. 19:30 · Английский · DoD: 20 карточек + 15 мин подкаста, 5 фраз выписано

Первый блок через 1ч35м. Первый шаг: открыть задачу «Number of Islands».
Неделя: глубокая работа 4ч/8ч, результаты 1/3.
Отбой 23:30.
```
Если L2 оставил директиву с высоким приоритетом — она добавляется одной строкой (текст уже написан фоном, вызова модели нет). Мотивационных фраз нет.

### 13.3. Середина дня
Только если выполнение < 40% к 15:00 и до конца дня есть задачи. Одно сообщение: факты + вопрос «что из оставшегося реально сделать?» → кнопки по задачам [Делаю] [Перенести] [Отменить].

### 13.4. Вечерний разбор — сердце системы
≤ 5 минут. Каждый шаг — кнопками, свободный текст — только для ответов на вопросы.

1. **Факты (L0):** выполнение обязательств, что не сделано и почему (коды причин), результат недели — прогресс, сон
2. **1–2 вопроса** под конкретный день. Источник: директива L2 прошлого анализа (`voice_hint`/вопрос) или L0-шаблон по фактам («3 старта сорваны с причиной "непонятно" — что было непонятно в задаче X?»). Ответы ловит FSM → `debrief_answered`. Кнопка [Пропустить] доступна
3. **Inbox** (если не пуст): [Разобрать сейчас — 2 мин] [Завтра]
4. **Долг** с истёкшим сроком решения — обязательный выбор (§6)
5. **План на завтра:** слоты шаблона завтрашнего дня, заполненные кандидатами (результаты недели → следующий шаг, долг, хвосты, узлы роадмапа). Пустой слот — бот спрашивает «что конкретно?» и предлагает варианты кнопками. Задача без DoD не попадает в план
6. **Подтверждение** [✅ Подтвердить] [✏️ Изменить в TWA] → `plan_confirmed` + `debrief_completed`
7. «Отбой в 23:30.»

После завершения — в фоне L2 `thinker` анализирует день; директивы будут использованы в завтрашних брифинге и разборе.

Пропущенный разбор — `debrief_missed` (цепочка прерывается), план на завтра собирается L0 из кандидатов автоматически и помечается «не подтверждён». Утром в брифинге — [✅ Подтвердить план].

### 13.5. Недельное планирование — §3.1

### 13.6. Месячный разбор (1-е число, ~20 мин)
Цели (актуальны? метрика двигается?), роадмапы (прогресс, ревизия источников), бюджет времени (повышение/понижение по правилу §3.2), автономность, профиль (данные интервью ещё верны?). Готовит L2 заранее, проходит в TWA + чате.

## 14. Опционально: финансы

Не входит в основной план (12-DECISIONS D15). Подключается, если одна из целей — денежная (накопить на ноутбук, курс).

- Ввод: `/spend 1200 еда` или два тапа в TWA. Флаг «импульсивная» — одной кнопкой
- Цель накопления с метрикой, связь с тратами: «Эта трата — 4 дня отката от цели "ноутбук"»
- Импульсивные траты — пункт разбора недели (что было триггером)
- Никаких банковских интеграций, номеров карт и инвестиционных советов
