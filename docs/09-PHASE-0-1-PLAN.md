## ФАЗА 0

### Шаг 0.1 · Инфраструктура
1. `docker-compose.yml`: postgres:16 (образ с pgvector), redis:7, core, caddy
2. `.env.example`: `BOT_TOKEN`, `OWNER_ID`, `DATABASE_URL`, `REDIS_URL`, `PUBLIC_URL`, ключи провайдеров
3. Caddy: реверс-прокси, автоматический TLS, раздача статики TWA
4. Alembic инициализирован, первая пустая миграция

**Проверка:** `docker compose up` поднимает всё, `/health` отвечает 200 по HTTPS.

### Шаг 0.2 · Модель данных
1. Модели из 03-DATA-MODEL: `events`, `profile`, `goals`, `traits`, `tasks`, `day_templates`, `biometrics`, `seasons`, `directives`, `devices`
2. Проекции: `state_daily`, `state_current`, `state_weekly`
3. `events/log.py`: функция `emit(kind, entity_id, payload, source)` — единственный способ записать событие
4. `projections.py`: `apply(event)` для инкремента + `rebuild()` для полного пересчёта
5. Тест-инвариант: сгенерировать 500 случайных событий → `rebuild()` даёт те же числа, что инкремент

**Проверка:** тест инварианта зелёный.

### Шаг 0.3 · Бот: скелет и онбординг
1. aiogram 3, фильтр `OWNER_ID` на всё
2. `/start` → если профиля нет → сообщение с inline-кнопкой Web App на экран онбординга
3. API `POST /api/onboarding/core` — 6 полей Стадии 1
4. После сохранения → бот присылает подтверждение и первый план на завтра

**Проверка:** с нуля дошёл от `/start` до заполненного профиля и плана.

### Шаг 0.4 · Шаблоны дней и материализация
1. Дефолтные шаблоны: Учебный, Рабочий, Глубокий, Восстановительный
2. `materialize.py`: шаблон + дата → набор задач в БД
3. Cron 04:30 — материализация на сегодня
4. Ручной запуск: `/day rebuild`

**Проверка:** утром в БД появляются задачи по шаблону дня недели.

### Шаг 0.5 · Напоминания и подтверждение
1. APScheduler с jobstore в Postgres (переживает рестарт)
2. Для каждой задачи: job на `T-5`, `T+0`, `T+duration`
3. Шаблоны сообщений в `bot/templates.py` — **чистые строки, без ИИ**
4. Inline-кнопки: Начать / Отложить 15 / Не смогу; Да / Частично / Нет
5. Обработчики пишут события, обновляют проекции, шлют WS-пуш
6. `proof=report` → FSM ждёт текст

**Проверка:** полный цикл задачи от напоминания до закрытия, всё в логе событий.

### Шаг 0.6 · API и WebSocket
1. `auth.py`: валидация `initData` (HMAC-SHA256 с токеном бота), зависимость FastAPI
2. Роуты: `GET/POST/PATCH /api/tasks`, `GET /api/day`, `GET /api/week`, `GET /api/state`, `GET/PATCH /api/profile`
3. `ws.py`: подключение с initData, подписка на Redis-канал, broadcast
4. Любое изменение состояния публикует в Redis → уходит в WS

**Проверка:** меняешь задачу через API — открытый WS получает сообщение.

### Шаг 0.7 · TWA v1
1. Vite + React + TS + Tailwind, Telegram WebApp SDK
2. Дашборд: состояние, задачи на сегодня, кнопки закрытия
3. Расписание: недельная сетка 7×24, скролл, drag-n-drop (`dnd-kit`), создание по тапу
4. TanStack Query + WS-инвалидация
5. Оптимистичные обновления

**Проверка:** закрыл задачу в чате → сетка в TWA обновилась без перезагрузки. И наоборот.

### Шаг 0.8 · L1: первый ИИ
1. `providers/base.py` — протокол; `groq.py`, `gemini.py` — реализации
2. `router.py`: роли из YAML, fallback-цепочка, таймауты, rate-limiter (token bucket), retry с backoff на 429
3. `constitution/` — секции v1 (identity, mission, voice, autonomy_rule, decision_rule, honesty, boundaries, safety_override)
4. `context.py` — сборка контекст-пакета из БД (цель: < 50 мс, замерять)
5. 4 инструмента: `get_day`, `create_task`, `complete_task`, `propose_schedule_change`
6. Стриминг в Telegram через `edit_message_text` с троттлингом раз в 400 мс

**Проверка:** написал «Арвикс, я в 15:00 хочу погулять» — получил осмысленный вердикт с реальными цифрами за < 2 сек.

### Шаг 0.9 · Ритуалы
1. Утренний брифинг по шаблону + одна фраза от модели
2. Вечерний разбор в 22:30: факты из БД + 2 вопроса от модели + план на завтра на подтверждение
3. `/debrief` — ручной запуск

**Проверка:** 7 дней подряд без ручного вмешательства.

### 🎯 Критерий завершения фазы 0
Неделя реального использования: план материализуется, напоминания приходят, задачи закрываются, брифинг и разбор идут, чат и TWA синхронны.

## ФАЗА 1

### Шаг 1.1 · Голос
1. `fewshot.py` — 8 примеров из 04-AI-LAYER §4
2. Тон-блоки: 4 файла, подстановка из Guard
3. `validators.py`: проверка источников, чисел, длины, стоп-слов в 🟥
4. Порядок промпта: статика → динамика (для кэша). Замерить экономию

**Проверка:** слепой тест — по 10 ответам ты узнаёшь Арвикса, а не «вежливого ассистента».

### Шаг 1.2 · Ручная биометрия
1. Экран утреннего ввода в TWA (5 полей), команда `/sleep`
2. Таблица `biometrics`, событие `sleep_recorded`
3. Напоминание о вводе при первом контакте утром

### Шаг 1.3 · Burnout Guard
1. `guard.py` — расчёт режима из 02-MECHANICS §6, чистая функция
2. Пересчёт: утром после ввода сна, при закрытии/провале задачи, в 15:00
3. Событие `mode_changed`, индикатор в TWA и в брифинге
4. **Тест:** при `mode = RED` сборщик контекста не содержит ни одного жёсткого тон-блока
5. **Тест:** при `mentor_enabled = false` — то же самое

### Шаг 1.4 · Safety-контур
1. Детекция: список маркеров + один дешёвый классификационный вызов при срабатывании
2. `raise_flag` → `mentor_enabled = false`, событие `safety_flag`
3. Переключатель в настройках TWA — единственный способ вернуть режим
4. Analyst игнорирует такие периоды при разборе эффективности

### Шаг 1.5 · Ledger
1. `ledger.py`: XP по формуле, уровни, HP по таблице урона, регенерация, щиты
2. Сезоны: `seasons`, расчёт SP, смена ранга, старт нового сезона
3. Все начисления — только через события. Ни одного прямого UPDATE
4. Отображение в TWA и в `/status`
5. Тест: последовательность из 30 дней даёт ожидаемые XP/HP/ранг

### Шаг 1.6 · Долг
1. Автоперевод проваленных `importance ≥ 4` в долг
2. Блокировка создания необязательных задач при долге ≥ 2 — с объяснением причины
3. Красный блок в TWA, эскалация на 7-й день

### Шаг 1.7 · Бюджет, типы дней, квоты
1. `budget.py`: недельный бюджет, прогрессия, проверка при добавлении задач
2. Типы дней в настройках, привязка к дням недели
3. `quotas.py`: подсчёт, подсветка со среды, автовставка в четверг, штраф в воскресенье
4. Полоски квот в TWA

### Шаг 1.8 · Память и интервью
1. `memory_facts` + эмбеддинги + инструмент `remember`
2. Отбор в контекст: топ-3 важных всегда + 5 по векторной близости
3. Интервью Стадии 2: очередь вопросов, по 1-2 в день, вплетение в разбор
4. Уточняющие переспросы при размытом ответе

### Шаг 1.9 · Протокол игнора и тихие дни
1. Счётчик дней молчания, эскалация по таблице 02-MECHANICS §7
2. Заморозка штрафов на 3-й день, протокол возвращения
3. `/silent` и автоматический тихий день раз в неделю
4. Autonomy Score v1: формула, отображение в TWA

### 🎯 Критерий завершения фазы 1
Две недели использования, за которые: режим переключался минимум дважды, щит сработал минимум раз, один тихий день пройден, Арвикс задал минимум 10 вопросов интервью и профиль заметно наполнился.

## Порядок работы с Claude Code

1. Дать ему `README.md` + `00-VISION.md` + `01-ARCHITECTURE.md` как постоянный контекст (`CLAUDE.md` в корне репозитория со ссылками)
2. Работать **по одному шагу за сессию**. Шаг = один PR = один коммит
3. Перед каждым шагом — прочитать соответствующий раздел спецификации
4. После каждого шага — прогнать тесты и запустить локально
5. Не давать ему писать сразу всю фазу: контекст переполнится, качество упадёт

### Что положить в `CLAUDE.md`
```markdown
# Arvix
Личный ИИ-ментор. Спецификация в docs/ — читай перед работой.

## Незыблемые правила
1. Всё, что можно сделать кодом — делается кодом. ИИ только там, где нужно понимание языка.
2. Совет моделей никогда не в цепочке ответа пользователю.
3. Любое изменение состояния — через события в events. Никаких прямых UPDATE проекций.
4. Имена моделей — только из конфига, никогда в коде.
5. В режиме RED и при mentor_enabled=false жёсткие тон-блоки не попадают в промпт. Это тестируется.
6. Один пользователь. Никакой мультитенантности, ролей и биллинга.

## Команды
make up / make test / make migrate / make lint
```
