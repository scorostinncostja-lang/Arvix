# 01 · Архитектура

## 1. Три слоя

Главное архитектурное решение проекта. Оно решает конфликт «мгновенный ответ» ⊥ «совет из нескольких моделей».

```
┌───────────────────────────────────────────────────────────────┐
│  L2 · СОВЕТ (фон, никто не ждёт)                              │
│  Триггеры: 04:30 ночь · 22:30 разбор · вс 20:00 ретро ·        │
│            3 провала подряд · смена режима Burnout Guard      │
│  Модели: Analyst (DeepSeek) · Planner (Gemini) · Vision        │
│  Выход: ДИРЕКТИВЫ в БД (не текст пользователю)                │
└────────────────────────────┬──────────────────────────────────┘
                             │ читает директивы
┌────────────────────────────┴──────────────────────────────────┐
│  L1 · ГОЛОС (0.4–1.5 с, 1 вызов)                              │
│  Всё, что пишется в чат. Быстрая модель (Groq).               │
│  Вход: Конституция (кэш) + Контекст-пакет + Few-shot + Tools  │
│  Выход: текст + вызовы инструментов                           │
└────────────────────────────┬──────────────────────────────────┘
                             │ вызывает инструменты
┌────────────────────────────┴──────────────────────────────────┐
│  L0 · РЕФЛЕКСЫ (0 мс, без ИИ)                                 │
│  Планировщик · напоминания · таймеры · XP/HP/стрики ·          │
│  Burnout Guard · квоты · Event Log · WebSocket-синк            │
│  Это 70% всего функционала Арвикса                            │
└───────────────────────────────────────────────────────────────┘
```

### L0 — Рефлексы

Работает всегда, даже если все LLM-провайдеры лежат. Чистый Python, никаких вызовов моделей.

| Модуль | Ответственность |
|---|---|
| `scheduler` | Материализация расписания в задачи, напоминания до/после, эскалация |
| `ledger` | XP, HP, стрики, сезоны, щиты, долг — всё по формулам из 02-MECHANICS |
| `guard` | Расчёт режима Burnout Guard из биометрии и выполнения. Меняет тон-блок для L1 |
| `quotas` | Недельные минимумы по сферам, подстановка невыполненных квот в план |
| `events` | Append-only лог, проекции состояния |
| `sync` | WebSocket pub/sub: любое изменение → мгновенно в TWA и в чат |
| `iot` | WebSocket-сервер для ESP32, команды и телеметрия |

**Правило:** если функцию можно описать формулой или таблицей решений — она в L0. Модели про неё даже не знают, они только читают результат.

### L1 — Голос

Единственный слой, который разговаривает. Один вызов модели на сообщение. Никаких цепочек, никакого «сначала спросим Gemini».

Структура вызова описана в 04-AI-LAYER. Коротко:
- **Конституция** — статичная, кэшируется провайдером (prompt caching), ~1200 токенов
- **Тон-блок** — подставляется из Burnout Guard, один из 4 вариантов, ~200 токенов
- **Контекст-пакет** — собран кодом, ~800–1500 токенов
- **Few-shot** — 8 примеров голоса, ~600 токенов
- **Инструменты** — JSON-схемы функций
- **История** — последние 10 сообщений, сжатие старых

Итого ~3500–4500 токенов на вход. На Groq это 0.4–1.2 сек до первого токена, стриминг в Telegram через редактирование сообщения.

**Fallback-цепочка:** Groq → Gemini Flash → DeepSeek. Таймаут 3 сек на провайдера. Если все упали — L0 отвечает шаблоном («Связь потеряна. План на день в приложении. Работай.») и ставит сообщение в очередь на разбор.

### L2 — Совет

Никогда не блокирует пользователя. Запускается по расписанию и по событиям, пишет результат в таблицу `directives`.

| Роль | Модель (конфиг) | Задача |
|---|---|---|
| **Analyst** | DeepSeek (дёшево, длинный контекст) | Разбор дня/недели: что сработало, где паттерн, где враньё в отчётах |
| **Planner** | Gemini Flash | Пересборка матрицы задач под режим, бюджет и квоты |
| **Researcher** | Gemini / Groq | Роадмапы обучения, подбор источников, проверка их актуальности |
| **Vision** | Gemini Flash (vision) | Фотоотчёты |
| **Chief** | Мини-модель OpenAI | Сводит выводы Analyst+Planner в 3-7 директив. Вызывается ~2 раза в сутки |

**Директива** — структурированная запись, которую L1 читает как факт:
```json
{
  "id": "dir_8814",
  "kind": "focus" | "warning" | "schedule_change" | "insight" | "quota_push",
  "text": "Вторники: выполнение 31% против 68% в среднем. Причина — смена накануне. Глубокую работу во вторник переносим на 07:00–09:00.",
  "voice_hint": "Напомни про вторник, если он попытается поставить задачу на вечер вторника",
  "valid_until": "2026-09-28",
  "priority": 2
}
```

L1 получает 3-5 активных директив в контекст-пакете. Так «ум совета» доходит до пользователя с задержкой быстрой модели.

## 2. Компоненты

```
                          Telegram
                       ┌─────┴─────┐
                  бот ─┤           ├─ TWA (React)
                       └─────┬─────┘
                             │ HTTPS + WebSocket
                    ┌────────┴────────┐
                    │   arvix-core    │  FastAPI + aiogram 3
                    │  (один процесс) │  L0 + L1 + API + WS
                    └────┬───────┬────┘
              ┌──────────┘       └──────────┐
        ┌─────┴─────┐               ┌───────┴───────┐
        │ PostgreSQL │               │     Redis     │
        │ + pgvector │               │ очереди/pubsub│
        └───────────┘               └───────┬───────┘
                                            │
                              ┌─────────────┴─────────────┐
                              │      arvix-worker         │  L2 + индексация
                              │  (ARQ / APScheduler)      │
                              └─────────────┬─────────────┘
                                            │
                    ┌───────────────┬───────┴──────┬──────────────┐
                    │  LLM-провайд. │ Obsidian git │  ESP32 (WS)  │
                    └───────────────┴──────────────┴──────────────┘
```

### Почему один процесс для бота и API
Один пользователь. Разносить на микросервисы — чистые накладные расходы. `aiogram` и `FastAPI` живут в одном asyncio-цикле, WebSocket-хаб общий, состояние в Postgres. Worker вынесен отдельно, потому что L2 может думать минуту и не должен блокировать event loop.

## 3. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык | Python 3.12 | aiogram, экосистема LLM, быстро писать |
| Бот | aiogram 3 | Нативный async, FSM, Web App из коробки |
| API/WS | FastAPI + uvicorn | Один процесс с ботом, Pydantic-валидация |

| Очередь задач | ARQ | Нативно async, легче Celery |
| Планировщик | APScheduler (в core) | Cron-триггеры, persistent jobstore в Postgres |
| Миграции | Alembic | — |
| ORM | SQLAlchemy 2 (async) | — |
| TWA | React 18 + Vite + TypeScript | — |
| Стейт TWA | Zustand + TanStack Query | Лёгкий, без бойлерплейта |

| Бэкапы | pg_dump в cron + дамп в Obsidian-репо | П6 |

### Абстракция провайдеров — обязательна

```python
class LLMProvider(Protocol):
    async def complete(
        self, messages: list[Message], tools: list[Tool] | None,
        max_tokens: int, temperature: float, stream: bool
    ) -> Completion: ...
```

Роли маппятся на модели **через конфиг**, не через код:

```yaml
roles:
  voice:      { provider: groq,     model: "<id>", timeout: 3,  temp: 0.8 }
  analyst:    { provider: deepseek, model: "<id>", timeout: 90, temp: 0.3 }
  planner:    { provider: gemini,   model: "<id>", timeout: 60, temp: 0.4 }
  researcher: { provider: gemini,   model: "<id>", timeout: 90, temp: 0.5 }
  vision:     { provider: gemini,   model: "<id>", timeout: 30, temp: 0.2 }
  chief:      { provider: openai,   model: "<id>", timeout: 60, temp: 0.5 }
fallback:
  voice: [gemini, deepseek]
```

**Точные ID моделей проверяются при развёртывании** — линейки меняются каждые месяцы. В коде не должно быть ни одного захардкоженного имени модели.

### Ограничения бесплатных тиров — учесть
Бесплатный тир Groq ограничен по запросам в минуту и по токенам в минуту. Для одного пользователя этого хватает с запасом при условии, что **совет не вызывается на каждое сообщение**. Это ещё одна причина архитектуры из §1. В `LLMProvider` — обязательный rate-limiter с очередью и экспоненциальным backoff на 429.

## 4. Ключевые потоки

### 4.1. Сообщение в чат
```
Telegram → aiogram → ContextBuilder (Postgres, ~15 мс)
  → LLMProvider[voice] (стриминг)
  → инструменты? → L0 выполняет → результат обратно в модель (макс. 2 круга)
  → ответ пользователю + Event Log + WS-пуш в TWA
```
Бюджет: **до 1.5 сек** до первого токена. Если ContextBuilder дольше 50 мс — это баг.

### 4.2. Напоминание (проактив, без ИИ)
```
APScheduler (T-5 мин) → L0 берёт задачу → шаблон сообщения → Telegram
APScheduler (T+длительность) → «Выполнил?» + инлайн-кнопки
  → ответ → L0 начисляет → Event Log → WS → TWA обновилась
```
Ноль вызовов модели. Модель подключается только если ответ свободным текстом или задача важная (нужен разбор).

### 4.3. Изменение расписания из чата
```
«Арвикс, завтра в 15:00 гулять с подругой»
  → L1 (voice) вызывает tool propose_schedule_change(...)
  → L0 проверяет: конфликты? бюджет недели? квоты? выполнение сегодня?
  → возвращает модели факты (не решение)
  → модель формулирует вердикт голосом Арвикса
  → если одобрено → tool apply_schedule_change → WS → TWA обновилась мгновенно
```
**Важно:** решение «да/нет» принимает не модель произвольно — L0 отдаёт ей жёсткие факты (у тебя выполнено 2 из 7, бюджет глубокой работы недобран на 4ч, квота «социум» на неделе закрыта 0/2). Модель формулирует, но опирается на цифры.

### 4.4. Вечерний разбор
```
22:30 → L0 собирает день → worker: Analyst (что случилось) + Planner (план на завтра)
  → Chief сводит в директивы → L0 сохраняет → L1 пишет разбор в чат голосом Арвикса
```
Пользователь ждёт только последний шаг.

## 5. Безопасность и приватность

- Single-user: все хендлеры проверяют `user_id == OWNER_ID`, всё остальное молча игнорируется
- TWA: валидация `initData` по HMAC-SHA256 с токеном бота при каждом запросе
- ESP32: UUID-токен устройства, ротация через TWA, привязка к `device_id`
- Секреты: `.env`, никогда в git. В репозитории — `.env.example`
- Данные не покидают твой VPS, кроме контента, отправляемого в LLM API
- **Фильтр приватности перед отправкой в LLM:** заметки и сообщения проходят через маскирование паролей/токенов/номеров карт по регуляркам
- Бэкап: ежедневный `pg_dump` + шифрованная копия в Obsidian-репозиторий
