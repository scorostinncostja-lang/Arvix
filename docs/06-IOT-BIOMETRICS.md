# 06 · Состояние тела, биометрия и IoT

## 1. Утренний чек-ин — основной источник (фаза 1)

Сон и самочувствие — главные входы Burnout Guard. Ручной ввод даёт ~80% пользы автоматики за 10 секунд в день.

**Чек-ин в чате** (wake + 10 мин, формат — 02-MECHANICS §13.1):
- Сон: время отхода и подъёма. По умолчанию — целевые из профиля, подтверждаются одной кнопкой
- Энергия 1–5 — одна кнопка
- Стресс 1–5 — опционально, раз в день не чаще

**Из текста:** `/checkin 23:40-07:15 3` или свободно «спал часов пять, энергии ноль» → L1 вызывает `log_checkin`.

**В TWA:** форма из 3 полей.

Событие: `checkin_recorded(sleep_min, bedtime, wake_time, energy, stress?, source=manual)`.

Почему не больше полей: каждое поле — трение каждый день. SpO2 и пульс в покое интересны, но решений почти не меняют.

## 2. Как состояние влияет на систему

Все реакции детерминированные, в L0. Никаких очков и «урона» — только изменение плана и тона.

| Сигнал | Реакция |
|---|---|
| Сон < 6 ч (1 ночь) | Строка в брифинге, глубокая работа сдвигается на утро, если есть слот |
| Сон < 6 ч в 2 из 3 ночей | 🟨: план −30%, глубокая работа до 13:00 |
| Сон < 5 ч три ночи | 🟥: только сон, еда, движение, один шаг |
| Энергия ≤ 2 два дня | 🟨 + вопрос в разборе о причине |
| Энергия = 1 два дня | 🟥 |
| Стресс ≥ 4 два дня | 🟨 + в план вставляется восстановительный блок (прогулка 30 мин) |
| Отбой позже целевого на 2+ ч | Вопрос в разборе; за 30 мин до отбоя на следующий день — напоминание |
| Шаги < 3000 (фаза 5) | Напоминание о движении, прогулка в свободный слот |
| Пульс покоя > средней за 14 дней на 10% (фаза 5) | Флаг «возможна перегрузка» в разбор, рекомендация лёгкого дня |

### Разговор при нарушении сна
Арвикс не штрафует — он спрашивает и действует:
1. «Сон 5ч20м. Что было?» → кнопки: [Не мог уснуть] [Залип в телефоне] [Работа/учёба] [Другое]
2. «Не мог уснуть» 2+ раза за неделю → директива по гигиене сна: экран за 60 мин до сна, свет, кофеин после 15:00, температура в комнате
3. «Залип» → это не бессонница, а триггер → `traits(kind=trigger)` и предложение плана «если-то» («если 23:00 — то телефон на зарядку в коридор»)
4. Неделя контроля: напоминание за 30 мин до отбоя каждый вечер

**Важно:** Арвикс не ставит диагнозов и не назначает средств. Только режим, рутина и вопросы. Устойчивые проблемы со сном — повод к врачу, и бот так и говорит.

## 3. Автоматическая биометрия (фаза 5, опционально)

### Ключевое ограничение
У Huawei **нет публичного API** для физических лиц. Huawei Health Kit требует одобренного аккаунта разработчика — для личного проекта практически нереально. Это самый рискованный элемент проекта, поэтому он в самом конце и опционален.

### Единый интерфейс, три реализации
```python
class BiometricsProvider(Protocol):
    kind: Literal["manual", "healthconnect", "export"]
    async def fetch(self, day: date) -> BiometricsRecord | None: ...
```
Guard, планирование и аналитика работают с `BiometricsRecord` и **не знают**, откуда он пришёл. Ручной чек-ин — это провайдер `manual`. Автоматика перекрывает только те поля, которые реально приходят; энергия и стресс остаются ручными.

### `healthconnect`
```
Huawei Band → Huawei Health (Android) → Health Connect → arvix-bridge (Kotlin, ~300 строк)
  → POST /api/biometrics (токен устройства)
```
- Читает `SleepSessionRecord`, `StepsRecord`, `HeartRateRecord`
- WorkManager: синхронизация раз в час
- Токен устройства — из TWA (QR)

**Проверить до начала работы (таймбокс 1 день):** пишет ли Huawei Health нужные поля в Health Connect на твоём телефоне. Не пишет — фаза закрывается, остаётся ручной ввод, система не ломается.

### `export`
Ручная выгрузка данных из Huawei Health → архив → парсер. Для разовой заливки истории.

## 4. Умный таймер на ESP32 (фаза 5, опционально)

### Назначение
Физическая кнопка входа в работу. Смысл — **начать фокус-блок, не беря в руки телефон**, потому что телефон и есть главный источник срыва. Это прямое продолжение протокола старта (02-MECHANICS §5): старт — самое трудное, и устройство на столе делает его на одно действие короче.

Инженерная часть (BOM, распиновка, пайка, корпус) — [10-ESP32-BUILD.md](10-ESP32-BUILD.md). Прошивка — `firmware/arvix-timer/`.

### Комплектующие (кратко)
ESP32 NodeMCU (USB-C) · OLED SSD1306 128×64 I2C · матричная клавиатура 4×4 · WS2812B (1 шт.) · пассивный зуммер + транзистор · отдельная кнопка «стоп».

### Индикация (WS2812)

| Цвет | Смысл |
|---|---|
| 🔵 Синий ровный | Фокус-блок идёт |
| 🟢 Зелёный | Перерыв |
| 🔴 Красный ровный | Время сна — устройство молчит, дисплей приглушён |
| 🔴 Красный мигание | < 5 минут до конца блока |
| 🟡 Жёлтый | Нет связи с сервером, работает офлайн |
| 🟣 Фиолетовый пульс | Арвикс ждёт действия: блок по плану начался, а старта нет |

### Клавиатура

| Код | Действие |
|---|---|
| `1#` | Старт текущей задачи из плана (= кнопка [▶️ Начал]) |
| `2#` | Старт перерыва |
| `<минуты>#` | Произвольный таймер (например `45#`) |
| `A` | Пауза / продолжить |
| `B` | Показать следующую задачу |
| `C` | Текущая задача: сделано |
| `D` | Завершить досрочно (запишется как прерывание) |
| `*` | Статус: обязательства дня, следующий блок, режим |
| Кнопка | Аварийный стоп |

### Протокол
**WebSocket** к серверу (`wss://<домен>/ws/device`) — сервер должен уметь пушить.

```
Устройство → Сервер:
  {"t":"hello","token":"<uuid>","fw":"1.1.0"}
  {"t":"session_start","task_id":"...","minutes":90,"at":...}
  {"t":"session_end","completed":true,"interruptions":2,"actual_min":87,"at":...}
  {"t":"key","code":"C"}
  {"t":"heartbeat","uptime":...,"rssi":-58}

Сервер → Устройство:
  {"t":"state","phase":"work|break|sleep|idle","remaining_s":2340,
   "task":"Алгоритмы: графы","next":"18:00 Английский","completion":"3/7","mode":"yellow"}
  {"t":"beep","pattern":"end|alert|ok"}
  {"t":"nudge","text":"БЛОК НАЧАЛСЯ"}
```

`session_start` с устройства = событие `task_started` + `focus_session` по окончании. Прерывания идут в аналитику стартуемости.

**Изменение относительно v1.0:** поля `hp` и `xp` из сообщения `state` убраны (геймификации больше нет). Прошивка (`include/types.h`, `src/net_client.cpp`, `src/display_ctl.cpp`) обновляется при начале фазы 5: в подвале экрана вместо `HP/XP` — `completion` и `mode`.

### Офлайн-режим — обязателен
- При потере Wi-Fi таймер **продолжает работать локально**
- События буферизуются в NVS (кольцевой буфер, ~50 записей)
- При восстановлении связи — дозапись с исходными таймстампами
- Устройство — тонкий клиент: никакой бизнес-логики, все решения считает сервер

Токен вводится **не в коде** — через портал настройки Wi-Fi при первом включении или через QR из TWA.
