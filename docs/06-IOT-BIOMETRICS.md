# 06 · IoT и биометрия

## 1. Умный таймер на ESP32

### Назначение
Физическая кнопка входа в работу. Смысл — **запустить фокус-сессию, не беря в руки телефон**, потому что телефон и есть главный источник срыва.

### Комплектующие (BOM)

| Компонент | Модель | Примечание |
|---|---|---|
| Микроконтроллер | **ESP32-S NodeMCU Type-C** | 30-pin, USB-C |
| Дисплей | OLED **SSD1306** 128×64, I2C | Время, фаза, таймер |
| Клавиатура | Матричная **4×4** | 8 пинов |
| Индикация | **WS2812B** (1 шт., адресный RGB) | Вместо трёх отдельных LED — экономит пины |
| Звук | Пассивный зуммер + транзистор | **Обязательно.** Свет не заметишь, звук заметишь |
| Кнопка | Тактовая, отдельная | «Стоп/паника», не через клавиатуру |
| Питание | USB-C 5V, 2A | — |
| Корпус | Печать / готовый | По вкусу |

### Распиновка (черновик, фиксируется при сборке)

```
I2C (OLED):   SDA = GPIO21, SCL = GPIO22
Клавиатура:   ряды  GPIO13, 12, 14, 27
              столбцы GPIO26, 25, 33, 32
WS2812:       GPIO4
Зуммер:       GPIO18
Кнопка стоп:  GPIO19 (INPUT_PULLUP)
```
⚠️ Не использовать GPIO 6-11 (флеш), GPIO 34-39 (только вход), GPIO 0/2/15 (boot-стрэппинг).

### Индикация (WS2812)

| Цвет | Смысл |
|---|---|
| 🔵 Синий (ровный) | Фокус-сессия идёт |
| 🟢 Зелёный | Перерыв |
| 🔴 Красный (ровный) | Режим сна — устройство молчит, дисплей приглушён |
| 🔴 Красный мигание | Меньше 5 минут до конца блока |
| 🟡 Жёлтый | Нет связи с сервером, работает в офлайне |
| 🟣 Фиолетовый пульс | Арвикс требует действия (непрочитанный вопрос) |

### Клавиатура — коды

| Код | Действие |
|---|---|
| `1#` | Старт фокус-блока по текущей задаче из плана |
| `2#` | Старт перерыва |
| `<минуты>#` | Произвольный таймер (например `45#`) |
| `A` | Пауза / продолжить |
| `B` | Следующая задача из плана |
| `C` | Отметить текущую задачу выполненной |
| `D` | Завершить сессию досрочно (запишется как прерывание) |
| `*` | Показать статус: HP, XP, выполнение дня |
| Кнопка | Аварийный стоп, всё гасится |

### Протокол

**WebSocket** к серверу (`wss://arvix.<домен>/ws/device`), не поллинг — сервер должен уметь пушить.

```
Устройство → Сервер:
  {"t":"hello","token":"<uuid>","fw":"1.0.2"}
  {"t":"session_start","task_id":"...","minutes":90,"at":...}
  {"t":"session_end","completed":true,"interruptions":2,"actual_min":87}
  {"t":"key","code":"C"}
  {"t":"heartbeat","uptime":...,"rssi":-58}

Сервер → Устройство:
  {"t":"state","phase":"work|break|sleep|idle","remaining_s":2340,
   "task":"Алгоритмы: графы","hp":68,"xp":640,"completion":"3/9"}
  {"t":"beep","pattern":"end|alert|ok"}
  {"t":"nudge","text":"ВЕРНИСЬ К РАБОТЕ"}
```

### Офлайн-режим — обязателен
- При потере Wi-Fi таймер **продолжает работать локально**
- События буферизуются в NVS (кольцевой буфер, ~50 записей)
- При восстановлении связи — дозапись на сервер с исходными таймстампами
- Индикация 🟡
- Устройство никогда не хранит бизнес-логику: XP, HP и решения считает сервер. Устройство — тонкий клиент с локальным таймером

### Прошивка — структура
```
main.cpp        — setup, loop, стейт-машина фаз
net.cpp         — WiFiManager (портал настройки при первом включении), WS-клиент, реконнект
display.cpp     — рендер экранов (idle / work / break / status / offline)
keypad.cpp      — опрос матрицы, дебаунс, парсер кодов
buffer.cpp      — NVS-буфер офлайн-событий
```

Токен вводится **не в коде** — через портал настройки Wi-Fi при первом включении или через QR из TWA.

## 2. Биометрия

### Ключевое ограничение
У Huawei **нет публичного API** для физических лиц. Huawei Health Kit требует одобренного аккаунта разработчика, получить который под личный проект практически нереально. Это самый рискованный элемент исходного ТЗ.

### Архитектура: единый интерфейс, три реализации

```python
class BiometricsProvider(Protocol):
    async def fetch(self, date: date) -> BiometricsRecord | None: ...
    @property
    def kind(self) -> Literal["manual", "healthconnect", "export"]: ...
```

Вся логика системы (Burnout Guard, XP-бонусы, планирование) работает с `BiometricsRecord` и **не знает**, откуда он пришёл. Смена источника = смена одной строки в конфиге.

### Реализация 1 — `manual` (**в MVP**)

Утренний ввод в TWA, 5 полей, ~20 секунд:
- Время отхода ко сну (по умолчанию — вчерашнее)
- Время подъёма
- Качество сна 1-5
- Самочувствие 1-5
- Стресс 1-5

Можно ввести из чата: `/sleep 23:40-07:15 4`.

**Это даёт 80% пользы.** Сон и субъективное состояние — главные входы Burnout Guard. SpO2 и пульс в покое приятны, но решений почти не меняют.

### Реализация 2 — `healthconnect` (фаза 5)

Единственный рабочий путь к автоматике:

```
Huawei Band 10 → Huawei Health (Android)
              → Health Connect (системное хранилище Android)
              → arvix-bridge (своё Android-приложение, ~300 строк Kotlin)
              → POST /api/biometrics на сервер
```

`arvix-bridge`:
- Читает Health Connect API: `SleepSessionRecord`, `StepsRecord`, `HeartRateRecord`, `OxygenSaturationRecord`
- WorkManager, синхронизация раз в час + при разблокировке
- Токен устройства из TWA (QR)
- Не имеет UI кроме экрана статуса

**Риски, которые проверяются до начала работы:**
- Пишет ли Huawei Health нужные поля в Health Connect (проверяется вручную за 10 минут)
- Стресс и SpO2 могут не экспортироваться — тогда остаются в ручном вводе
- Если Huawei Health перестанет писать в Health Connect — падаем на `manual`, система не ломается

### Реализация 3 — `export` (резерв)

Запрос выгрузки данных в Huawei Health → архив → парсер на сервере. Полные данные, но вручную и с задержкой. Держим как запасной вариант и как способ разово залить историю.

## 3. Как биометрия влияет на систему

| Сигнал | Реакция (детерминированная, в L0) |
|---|---|
| Сон < 6ч (1 день) | −6 HP, предупреждение в брифинге |
| Сон < 6ч (2 дня) | Режим 🟨, план −30%, глубокая работа только до 12:00 |
| Сон < 5ч (3 дня) | Режим 🟥, штрафы заморожены, задача дня — выспаться |
| Сон в норме | +15 XP, +8 HP |
| Отбой позже +2ч от целевого | −5 HP, вопрос в разборе |
| Стресс высокий 2 дня | Режим 🟨, вставка восстановительного блока |
| Шаги < 3000 | Напоминание о движении, вставка прогулки в план |
| Пульс покоя вырос >10% к средней за 2 недели | Флаг «возможна перегрузка» в разбор, −20% нагрузки |

### Разговор при нарушении режима
Арвикс не просто штрафует — он **спрашивает и действует**:
1. «Сон 5ч20м. Что было?» → варианты кнопками: не мог уснуть / залип / работа / другое
2. Если «не мог уснуть» 2+ раза за неделю → директива на гигиену сна: экран за 60 мин, свет, кофеин после 15:00, температура
3. Если «залип» → это не бессонница, это триггер — уходит в `traits` и разбирается как слабость
4. Контроль: в течение недели Арвикс проверяет отбой каждый вечер за 30 минут

**Важно:** Арвикс не ставит диагнозов и не назначает средств. Только режим, рутина и вопросы.
